# 雛形を新しい版に上げる

- **誰が実行するか**：上げるかどうかは人が決める。当てる作業は AI が手伝う。コミットの前に、人に結果を見せる
- **何が起きるか**：このプロジェクトに写した REI の雛形を、新しい版に合わせる。プロジェクトで書き足したところ（台帳・決めたこと・`START.md` の記入など）は残す
- やり方は、雛形からプロジェクトを作る道具の定番（Copier の `copier update` など）と同じ3方向マージ：**古い雛形と新しい雛形の差分だけを、プロジェクトに当てる**。新しい雛形で上から写すと、プロジェクトで書き足したところが消える

## 用意するもの

- 古い雛形：このプロジェクトを作ったときの版の `template/`。版は、受け取りの記録 `.rei/received.cfg` の `template.version` を見る（`git config --file .rei/received.cfg template.version`。下の「受け取りの記録」）。受け取りの記録が無いプロジェクトでは、`.claude/hooks/session-start.sh` の `rei=` を見る
- 新しい雛形：上げたい版の `template/`
- 手に入れ方：REI のリポジトリは、公開した版ごとにタグ（`v0.3.0-beta.N` の形。最初は v0.3.0-beta.38）を付ける。REI のリポジトリを clone して、版ごとに別々のフォルダへ、タグ全体を取り出す（例：`git -C <REI> archive v0.3.0-beta.38 | tar -x -C <版のフォルダ>` → 雛形は `<版のフォルダ>/template`）。`template` だけを取り出すと、隣の `changes.cfg`（版ごとの必須・手作業）が無く、一覧の「間の版」が出ない（v0.3.0-beta.32 からは、出せないと1行出る）。GitHub の タグの zip を取るときも、全体を展開する
- 変更点：REI の `CHANGELOG.md`（古い版から新しい版までの項目）

## まず試す（おすすめ）

本体の作業フォルダに直接当てる前に、別の作業フォルダ（git worktree）で試せる。本体には触らない。

```sh
bash scripts/upgrade-try.sh <古い雛形の template> <新しい雛形の template>
```

- 本体の隣に `<プロジェクト名>-rei-try` を作り（ブランチは作らない）、下の「流れ」の 2.〜5. を機械で行う：入れ替え・足すは写す、3方向は行末をそろえて `git merge-file`、消すは消す。見る・確かめるは当てずに並べる
- 確かめる：ぶつかりの印、bash の構文、JSON の書式、`check-received.sh`、点検の試験、本体の HEAD と状態が変わっていないこと、git の設定
- 報告は `.rei/reports/upgrade-try-<日時>.md`（git に入れない。手元のパスが入ることがあるので、記録に貼るときは消す）。影響の範囲（入れ替え・3方向・ぶつかり・見る……の数）は、このプロジェクトで計算した値
- **採る**：報告の手順（試しのフォルダで直してコミット → 本体で `git merge --ff-only`）
- **捨てる**：`bash scripts/upgrade-try.sh --discard`。試しを作ってからだれも手を加えていなければ、戻してから普通に消す。人が中を直していたら止まる（直したものを残すか、強制で消すかは人が決める：`git worktree remove --force`）
- 止まるとき：作業ツリーに未コミットの変更がある、前の試しが残っている（`--status`）、git のロックファイルがある（消さずに人に返す）
- 試しが残っていると、起動のときに知らせる
- Claude Code は起動しない（試しのフォルダで起動すると、別のプロジェクトとして記録ができる）

## 版を選んで取り込む

間の版を全部ではなく、選んだ版の変更だけを取り込める。たとえば、新しい hook だけ先に欲しいときに使う。

**実験的**：受け取りの記録があるプロジェクトで、REI の写しに版ごとのタグがあるときだけ使える。記録の無いプロジェクトは、まずふつうの上げ方で上げる。

```sh
bash scripts/upgrade-plan.sh --only <版>[,<版>…] <REI の写し>   # 見る
bash scripts/upgrade-try.sh  --only <版>[,<版>…] <REI の写し>   # 試しのフォルダで当てる（おすすめ）
```

- **REI の写し**：REI を clone したフォルダ（`changes.cfg` と、版ごとのタグ `v<版>` があるもの）。版の雛形は、タグから git の管理フォルダの中（`rei-versions/<版>/template`）に取り出す。git には入らない。消してもよい（次に要るとき、また取り出す）
- **当て方**：選んだ版ごとに、その版の雛形と1つ前の版の雛形の差分だけを、版の古い順に当てる（cherry-pick と同じ考え方）。`upgrade-try.sh` は版を1つ当ててから、次の版の一覧を出す
- **必須は飛ばせない**：受け取りの記録の版より後で、選んだいちばん新しい版より前の、まだ取り込んでいない必須の版（`changes.cfg` の `severity = required`）は、選ばなくても足す。推奨・任意の版は、選ばなければ取り込まない
- **記録の版は途切れずに取り込んだところまで**：`template.version` は、記録の版から途切れずに取り込み終わった版までしか進めない。飛ばして先に取り込んだ版は `[picked "<版>"] applied = YYYY-MM-DD` に書く（一覧と報告の「記録の書き方」にコマンドが出る）。進めすぎると、取り込んでいない版が知らせにも一覧にも出なくなる
- 受け取りの記録（`.rei/received.cfg`）そのものは、版ごとの差分では当てない（版の行がぶつかるため）。最後に「記録の書き方」のコマンドで書く
- 起動のときの知らせは、`[picked]` の版を数えない。あとで残りの版を取り込んで記録の版が追いついたら、含まれた `[picked]` は消す（一覧に `--remove-section` のコマンドが出る。`check-received.sh` は、記録の版に含まれた印が残っていると止める）
- 前の版で足されたファイルを、選んだ版が直していることがある（前提の版を取り込んでいない）。そのファイルは「確かめる」に出る。CHANGELOG を読み、前の版も取り込むかを決める
- `upgrade-plan.sh --only` の2つ目からの版は、前の版を当てる前のプロジェクトで見ている。当てるのは `upgrade-try.sh --only` で

## 流れ

1. **始める前**：作業中の変更をコミットしておく（あとで差分を見られるように）。ブランチを分けるなら分ける
2. **何をするか出す**：プロジェクトのフォルダで `bash <新しい雛形>/scripts/upgrade-plan.sh <古い雛形> <新しい雛形>`（見るだけで、書き換えない。新しい雛形の側のスクリプトを使う。古いプロジェクトには、このスクリプトが無いことがある）。ファイルごとに「入れ替え・3方向・足す・消す・確かめる・済」が出る
3. **当てる**
   - 入れ替え・足す：新しい雛形のファイルを写す
   - 3方向：`git merge-file` を使う（2. で出たコマンド）。ぶつかった箇所は `<<<<<<<` の印が付くので、プロジェクトの書き足しを残して手で直す
   - 消す：名前が変わっただけのこともある（CHANGELOG を見る）。消してから新しい名前のファイルを足す
   - 見る：プロジェクトが書いていくファイル（下の「ファイルの持ち主」）。上書きも3方向もしない。出たコマンド（`diff`）で雛形の変わったところを読み、要るところだけ手で足す（`START.md` に問いが増えたときなど）
   - 確かめる：人に聞く
   - 受け取らない：受け取りの記録の `[skip]` にあるファイル。何もしない
   - 受け取りの記録の `version` は、全部当て終わってから最後に新しい版にする（先に変えると、一覧が「済」と出る）
4. **実行権限**：「（+x）」が付いたファイルは、`git add` のあとに `git update-index --chmod=+x <ファイル>`（Windows では写すと消える）
5. **確かめる**
   - `.rei/received.cfg` の `template.version` が新しい版になっている（記録の無いプロジェクトから上げたときは、このファイルが「足す」に出る）。`applied`（当てた日）・`decision`（7. で書く decisions/ のファイル名）・`claude-code`（`claude --version` の版）を書く
   - REI に試験があれば、プロジェクトのフォルダに流す（hook が新しい版で動くか）
   - `.claude/stop-requested` が残っていない
6. **人に知らせる**：`START.md` などに新しい問いや欄が増えていたら、上げた直後に人に知らせて、一緒に埋める（`AGENTS.md` 1.）
7. **記録する**：`decisions/` に版を上げたことを1つ書く（古い版・新しい版・ぶつかったところ・やり残したこと）。コミットする

## 受け取りの記録（`.rei/received.cfg`）

REI から何を・どの版で受け取ったかの記録。雛形に入っていて、プロジェクトを作ったときに一緒に写る。Copier の `.copier-answers.yml`、cruft の `.cruft.json` と同じ役目。

- 書式は git の設定ファイルと同じ（`[節]` と `項目 = 値`）。読む・書くのは git で：`git config --file .rei/received.cfg template.version`、`git config --file .rei/received.cfg template.applied YYYY-MM-DD`
- 項目（`[template]`）

  | 項目 | 中身 | 誰が書くか |
  |---|---|---|
  | `version` | 受け取った雛形の版（REI の `CHANGELOG.md` の見出しと同じ） | 雛形に入っている。版を上げたら新しい版になる |
  | `commit` | 受け取った雛形のコミット（タグが付け直されても分かるように） | プロジェクトを作るとき・版を上げるとき：`git -C <REI> rev-parse 'v<版>^{commit}'` |
  | `source` | どこから受け取ったか | 雛形に入っている |
  | `applied` | 作った日・最後に版を上げた日（YYYY-MM-DD） | プロジェクト |
  | `decision` | 版を上げたことを書いた `decisions/` のファイル名 | プロジェクト |
  | `claude-code` | 当てて試した Claude Code の版（`claude --version`） | プロジェクト |

- 個人の名前・アカウント名・手元の絶対パスは書かない
- 手で直すときは、`git config --file` を使うか、書式を崩さない（項目の名前は英数字と `-` だけで、`_` は使えない。1行でも崩れると、ファイル全体が読めなくなる。そのときは起動のときに「版の記録が読めません」と出る。直すには `git config --file .rei/received.cfg --list` でどの行かを見る）
- 後の版で節が増える（ファイルを受け取らないと決めた印、ほかのリポジトリから写したファイル、機能ごとの版）。知らない節は読み飛ばしてよい
- `[picked "<版>"] applied = YYYY-MM-DD`：版を選んで先に取り込んだ印（v0.3.0-beta.30。上の「版を選んで取り込む」）。`version` より新しい版だけに書く
- 版を上げるとき、このファイルは当てない（3方向にすると、雛形の `version` の行とプロジェクトの `commit` の行が隣り合ってぶつかる）。一覧には「残す」と出て、最後に `version`（と `commit`）だけを書く。`upgrade-try.sh` は試しのフォルダの記録に書いておく。`applied`・`decision`・`claude-code` は人が書く。記録の無いプロジェクト（beta.23 まで）には「足す」と出る
- コミットの前に `scripts/check-received.sh` が書式を見る（`.githooks/pre-commit` から。読めない・版が2行ある・版の形でない・`commit` や `applied` の形が違う、`AGENTS.md` に手元のパスがある、`.rei/local.cfg` を git に入れた、`[picked]` の版の形・日付が違う・`version` に含まれた印が残っている、なら止める）。版の形は `x.y.z` か `x.y.z-alpha.N`・`-beta.N`・`-rc.N`

## 手作業が要る版

`upgrade-plan.sh` の冒頭の「間の版」に、版ごとの重さ・必須の理由・手作業（REI の `changes.cfg` の `manual`）が出る。手作業のある版は、その版の CHANGELOG の「上げ方」を読んで、人と一緒にする。起動のときの知らせにも「手作業あり N」と出る。

## ファイルの持ち主（`.rei/owners.cfg`）

ファイルごとに、版を上げるときの当て方を決める表。雛形の持ち物で、プロジェクトでは書き換えない（版を上げると新しい雛形の表になる）。Copier の `_skip_if_exists` と同じ考え。

| 持ち主 | ファイル（例） | 当て方 |
|---|---|---|
| project（プロジェクト） | `GOAL.md`・`START.md`・`handoff.md`・`CHANGELOG.md`・台帳・作業記録 | 上書きも3方向もしない。雛形で変わったら「見る」 |
| shared（共有） | `AGENTS.md`・`CLAUDE.md`・`.claude/settings.json` | 3方向。JSON は当てたあと書式を確かめる（崩れると Claude Code は黙ってそのファイルを読み飛ばす） |
| 表に無いもの（雛形） | hook・点検のスクリプト・`docs/` | 手を加えていなければ入れ替え、加えていれば3方向 |

## 受け取らないファイル（`[skip]`）

雛形のファイルを、このプロジェクトでは受け取らないと決めたら、受け取りの記録に1つ1節で書く。版を上げるとき、そのファイルは「受け取らない」と出て、数えない（毎回「確かめる」に出なくなる）。

```sh
git config --file .rei/received.cfg 'skip.docs/glossary.md.reason' '辞書はプロジェクト独自'
```

- `reason`（理由）は必ず書く。理由の無い節は受け取らない扱いにならない
- 受け取らないと決めたことは、`decisions/` にも書く

## 新しい版の知らせ

起動のとき（`session-start.sh`）に、REI の写し（REI を clone したフォルダ）の `CHANGELOG.md` の一番上の版と、受け取りの記録の版を比べ、新しければ知らせる。間の版の重さ（必須・推奨・任意）は、写しの `changes.cfg` から数える。

- 写しのフォルダは `.rei/local.cfg`（機械ごとの設定。git に入れない）に、コマンドで書く：

  ```sh
  git config --file .rei/local.cfg copy.path 'C:\path\to\rei'
  ```

  手で書くときは `\` を `/` にする（`path = C:/path/to/rei`）。git の設定ファイルでは `\` が特別な文字で、そのままだと読めない。アカウント名を含むパス（`C:\Users\<名前>\…`）でも、このファイルは git に入らないので履歴には残らない（`.gitignore` に入っている）
- 知らせは2つに出す：人の画面（hook の `systemMessage`）と、AI に渡す文脈。人の画面に出すのは、新しい版があるとき・止めた印が残っているとき・記録が読めないとき・写しが未設定のとき（一度だけ）
- 知らせには「手元の写しを見ています（写しの最後のコミットの日）」を書き添える。写しが古いと、もっと新しい版があっても分からない。最後に比べた日は `.rei/local.cfg` の `copy.last-checked`
- 上げはしない。上げるかどうか・いつ上げるかは人が決める
- ネットには出ない。写しを新しくするのは人（`git -C <写し> pull`）
- **必須の版は飛ばさない**：止めるべきときに止まらない・外への書き込みを見逃す、などを直した版。後の版を当てる前に、間の必須の版を当てる（何版も飛ばして古い版と新しい版を直接比べるときは、間の必須の版の CHANGELOG を必ず読む）

## 状態とメニュー（`/rei`）とステータスライン

- **`/rei`**：Claude Code で `/rei` と打つと、REI の状態（このプロジェクトの版、新しい版と必須の数、版上げの試し、止めた印、ステータスライン）を出し、次にすることをボタンで聞く（新しい版を見る・試す・版を選ぶ・試しを捨てる・ステータスラインを付ける）。`/rei status` は状態だけ。AI が自分から使うことはない（人が打ったときだけ）。中身は `.claude/skills/rei/SKILL.md` と `scripts/rei-status.sh`（人が流してもよい。見るだけ）
- **ステータスライン**：画面の下に「REI 0.3.0-beta.31・新しい版 0.3.0-beta.32（必須 1）・/rei」のような1行を出す（`.claude/statusline.sh`）。**付けるかは人が選ぶ**（`/rei` の「ステータスラインを付ける」、または `/rei statusline-on`）。付けるときは自分だけの設定 `.claude/settings.local.json` に書く。共有の設定（`.claude/settings.json`）には書かない：プロジェクトの設定は個人の設定より優先されるので、ほかの人が自分で作ったステータスラインが消える
- 版の比べは起動のときだけ（`session-start.sh`）。結果を `.claude/rei-state`（git に入れない）に控え、ステータスラインと `/rei` はそれを読む。写しを新しくしたら、Claude Code を起動し直すと変わる
- 起動のとき人の画面に知らせを出すときは、終わりに「状態とメニューは /rei」と添える
- フォルダを信頼していないと、ステータスラインは出ない（公式 https://code.claude.com/docs/en/statusline 「Workspace trust required」）
- ステータスラインを付けると、画面の下の操作の案内（`esc to interrupt` など）が出なくなる（同じページの冒頭。Esc はそのまま効く）。`/rei` は付ける前にそう伝える
- 版は受け取りの記録からその場で読む。版を上げた直後は、起動し直すまで「新しい版」を出さない（控えが古い版のときのものだから）
- Claude Code は、プロジェクトのいちばん上のフォルダで起動する。下のフォルダで起動すると、REI の hook も設定も読まれず、知らせもステータスラインも出ない（公式 https://code.claude.com/docs/en/settings 「start Claude Code there」。`START.md` の冒頭にもある）

## 古い雛形を手に入れる

- 公開している版は、REI のリポジトリのタグ（`v0.3.0-beta.N`）から取り出せる。REI はタグを消さない・付け直さない
- **古い雛形には、そのプロジェクトを作ったときの本当の親を使う**。代わりの版を使うと、親との差が「プロジェクトでの変更」に見えて、3方向とぶつかりが増える。親が2つ混ざっているときは、「確かめる」に同じ名前のファイルとして出る。混ざったファイルは、人と一緒に読みながら直す

## 作り直すとき（上げる代わりに、新しい雛形から作り直す）

古い雛形（受け取りの記録も版の行も無い、版の分からないもの）は、上げるより作り直すほうが早いことがある。決めるのは人。比べるときは、`upgrade-plan.sh` の一覧（3方向・確かめるの数）と、下の引き継ぐものの量を見る。

- 新しい雛形から、別のフォルダにプロジェクトを作る（`git init`、受け取りの記録の `applied` に作った日）
- **引き継ぐもの**（プロジェクトが書いてきたもの。中身を写す）
  - `decisions/`（決定。番号もそのまま。書き換えない）
  - `ledger/`（`task_log.md`・`issue_log.md`・`incident_log.md`・`worklog/`）
  - `handoff.md`・`GOAL.md`・`START.md` の記入・`CHANGELOG.md`（プロジェクトのもの）
  - `docs/` でプロジェクトが足したもの（`docs/domains/` の分野の地図など）
  - プロジェクトの成果物（文章・資料・コードなど、雛形に無いファイル）
  - `AGENTS.md` でプロジェクトが足した節（プロジェクト独自の節）。雛形の節は新しいものを使う
- **引き継がないもの**：`.claude/hooks/`・`.claude/settings.json`・`.githooks/`・`scripts/` の雛形のもの（新しい雛形のものを使う）。プロジェクトで足した hook は、エントリを分けて足し直す（`docs/naming.md`「hook の書き方の決まり」）
- 古いリポジトリの履歴は、残すなら `git bundle create <名前>.bundle --all` で退避する（`docs/howto/backup.md`）
- 作り直したことを `decisions/` に書く（なぜ上げずに作り直したか）

## 外から入れるもの（プラグインなど）を上げるとき

- 自動更新は入れない（Claude Code のプラグインのマーケットプレイスも、Anthropic 以外のものは既定で切られている）
- 上げる前に CHANGELOG を読み、差分を見る。できれば別のブランチで試してから入れる（`policy.md` 3.）

## 気をつけること

| 場面 | どうする |
|---|---|
| プロジェクトの日本語のファイル名が `\343\201\223…` のように表示される | git の既定の表示。`git -c core.quotepath=false status` で名前を出す。表示をそのまま `git mv` に渡すと失敗するので、`git rm` と新しいファイルの追加に分けてもよい |
| `git merge-file` のあとで改行の警告が出る | 書き出したファイルの行末が LF になるため。害は無い |
| Windows で、取り出したプロジェクトの行末が CRLF、zip の雛形が LF | `upgrade-plan.sh` は行末の違いを中身の違いと見ないので、そのままでよい |
| 「（+x）」が多めに付く | Windows では、先頭が `#!` のファイルは実行できると見えるため。雛形の `.sh` に付けておけばよい |
| 同じプロジェクトの別のリポジトリ（`-web`・`-api` など）に点検（`scripts/check-*.sh`・`.githooks/pre-commit`）を写している | 2. で、それらのファイルが「入れ替え」「3方向」に出たら、そちらのリポジトリも同じように上げ、そちらの `CLAUDE.md` の「どの版から写したか」も直す（置き方は `docs/repos.md`） |
| 古い版が分からない | `.rei/received.cfg` の `template.version`、無ければ `session-start.sh` の `rei=` を見る。それも無ければ、いちばん近い版を古い雛形として使い、「確かめる」を多めに見る |
| 何版も飛ばして上げる | 古い版と新しい版を直接比べてよい。変更点は、その間の CHANGELOG の項目を全部読む |

## 限界

- `upgrade-plan.sh` は、ファイルの中身が同じかどうかだけを見る。中身の意味（決まりが変わったことで、プロジェクトの記録の書き方も変えるべきか）は見ない。CHANGELOG を読んで人と決める
